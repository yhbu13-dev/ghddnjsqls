# 운영 런북

운영팀(관제 담당)이 매일 보는 순서와, 콘솔 경보별 대응입니다. 시각은 기본 설정 기준이며 [관리 → 운영 설정]에서 바꿀 수 있습니다.

## 하루 흐름

| 시각 | 시스템이 하는 일 | 운영자가 할 일 |
|---|---|---|
| 21:00 ~ 09:00 | 이 시간에 생긴 발주 제안은 발송하지 않고 09:00로 예약합니다 | — |
| 09:00 | 예약된 제안을 일괄 발송합니다 | [관제 홈 → 지금 조치 필요] 확인 |
| 오전 | 사장님 응답 · 60분 뒤 자동 리마인드 · 3시간 무응답이면 만료(다음 날 10:00 재제안) | **승인 지연**은 전화로 확인한 뒤 [대리 승인]. 사유를 꼭 남깁니다 |
| 11:00 ~ 14:30 | 브레이크타임 선호 매장의 제안은 15:00로 예약합니다 | — |
| **12:00 컷오프** | 이후 결제된 발주는 다음 배송일로 넘어갑니다 | 컷오프 전에 **결제 실패**를 처리합니다 |
| **13:30 배차** | 권역별 라우트를 만들고 정차 순서와 ETA를 계산합니다 | [배송 관제]에서 **기사 링크**를 기사에게 보냅니다(하루 1회) |
| 오후 | 기사가 도착 → 잔량 입력 → 하차 완료를 처리하고, 사장님께 배송 완료 안내가 나갑니다 | 기사가 휴대폰을 못 쓰면 [오늘 정차 목록]에서 대신 처리합니다 |
| 매주 | 주차가 끝나면 정산이 마감됩니다 | [파일럿 리포트 → 티오더 정산]에서 CSV 내역서를 티오더에 전달하고, 지급을 확인하면 [지급 완료] |

## 경보별 대응 (관제 홈 · 지금 조치 필요)

| 유형 | 뜻 | 대응 |
|---|---|---|
| 결제 실패 | 승인했지만 결제가 거절됨 | 사장님께 결제 수단을 확인받은 뒤 [재결제]. 계속 실패하면 [취소]합니다 |
| 승인 지연 | 발송 후 30분 넘게 응답 없음 | [리마인드] → 그래도 응답이 없으면 전화 → 구두 승인이면 [대리 승인] |
| 승인 지연 · 검수 대기 | 추정 편차가 큰 매장이라 발송 전 확인이 필요함 | 수량을 확인하고 [검수 후 발송] |
| 재고 임박 | 몇 시간 안에 오차 밴드 하한이 안전재고에 닿을 예정 | 대개 자동 제안을 기다립니다. 급하면 [선제 제안] |
| 재고 임박 · 보류·미응답 후 대기 | 사장님이 보류했거나 응답이 없어 다음 날까지 재제안이 막혀 있음 | 결품 위험이 있으니 전화로 확인합니다 |
| POS 지연 | 영업 시간인데 45분 넘게 판매 로그가 없음 | 티오더 연동 상태와 매장 영업 여부를 확인합니다. 로그가 늦게 도착해도 자동으로 반영됩니다 |
| 초기 실사 | 잔량을 한 번도 입력하지 않은 매장 | [잔량 입력] — 입력 전에는 제안이 나가지 않습니다 |
| 발송 실패 | 메시지가 5회 재시도 후 실패 | [관리 → 데이터 연동]에서 원인을 보고, 웹훅 URL·대행사 상태를 확인합니다 |

## 매장 온보딩

1. [관리 → 매장 → 매장 등록]: 코드, 이름, 권역, 사장님 휴대폰, 주소·좌표, 티오더 매장 ID를 넣습니다.
2. [SKU]: 취급 SKU를 고릅니다. 판매 이력이 3일 쌓이기 전까지 쓸 **예상 일 판매량**을 넣으면 첫 주 제안이 정확해집니다.
3. [잔량]: 매장을 방문해 센 현재 잔량을 입력합니다.
4. 사장님께 발주 제안 링크를 받는 방법(알림톡, 초기에는 카카오톡 전달)을 안내합니다.

점심 피크에 응답이 늦는 매장은 발송을 **브레이크타임**으로 바꿉니다. 서비스·폐기가 많아 추정 편차가 큰 매장은 **검수 후 발송**을 켭니다.

## 추정 모델을 이해하는 법

- **추정 재고** = 마지막 실사 + 입고 − POS 판매 × (1 + 누수 보정 α)
- **오차 밴드** = 기본 폭 + 마지막 실사 이후 추정 소진량 × 밴드 증가율
- **트리거**: 추정값이 아니라 **밴드 하한**이 안전재고 이하가 되면 제안합니다. 추정이 빗나가도 결품이 먼저 오지 않게 하려는 설계입니다.
- **학습**: 기사가 하차 전에 센 잔량과 추정의 차이로 매장별 α를 조금씩 보정합니다(학습률 0.35).
- **묶음**: 트리거가 걸린 SKU와 함께, 앞으로 8일 안에 트리거될 SKU를 한 번에 채워 주 1회 배송에 맞춥니다.

## 배포

서버 설치·HTTPS·자동 백업은 `deploy/README.md`를 보세요.

## 백업 · 복구

```bash
npm run backup                         # backups/bevflow-YYYYMMDD-HHMM.db (실행 중에도 안전)
# 복구: 서버를 멈추고 파일을 교체
systemctl stop bevflow && rm -f data/bevflow.db-wal data/bevflow.db-shm && cp backups/bevflow-….db data/bevflow.db && systemctl start bevflow
```

`deploy/bevflow-backup.timer`(systemd)나 아래 크론으로 매일 백업하고, 백업 폴더를 다른 저장소(예: 오브젝트 스토리지)로 복사해 두세요.

```cron
0 4 * * * cd /opt/bevflow && /usr/bin/npm run backup >> /var/log/bevflow-backup.log 2>&1
```

## 보안

- 계정 권한: **관리자**(설정·계정·키), **운영자**(운영 조치·매장 관리), **열람**(조회만, 연락처는 가려짐)
- 사장님·기사 링크는 서명된 토큰입니다. 유출이 의심되면 [관리 → 데이터 연동 → 링크 서명 키 재발급]을 누르세요. 이미 보낸 링크가 모두 무효가 됩니다.
- POS 수신 키·웹훅 키도 같은 화면에서 재발급합니다. 상대 시스템에도 새 키를 반영해야 합니다.
- HTTPS 프록시 뒤에서는 `BEVFLOW_TRUST_PROXY=1`로 실행해야 세션 쿠키에 `Secure`가 붙습니다.

## 문제 해결

| 증상 | 확인할 것 |
|---|---|
| 사장님 링크가 열리지 않음 | [운영 설정 → 외부 접속 주소]가 실제 HTTPS 주소인지, 링크가 7일을 넘기지 않았는지 |
| 발주 제안이 안 나옴 | 매장이 **운영 중**인지, 초기 잔량이 들어갔는지, 보류·만료 후 재제안 대기 중이 아닌지, 이미 진행 중인 발주가 있는지 |
| 재고가 줄지 않음 | POS 메뉴가 매핑돼 있는지([미매핑 POS 메뉴]), 매장의 티오더 매장 ID가 맞는지 |
| 배차가 안 됨 | 오늘이 배송 요일인지, 권역에 **운영 중** 기사가 있는지. [지금 배차 실행]으로 수동 실행 |
| 비밀번호 분실 | 서버에서 `npm run create-admin -- 이메일` |
